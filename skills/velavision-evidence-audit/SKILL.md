# VelaVision 证据与提交核对

先把用户所指的版本、材料目录和提交目标变成可复核清单，再写结论。默认离线，只读原始证据；输出到用户指定的新目录。此 Skill 于 2026-11-03 提交整理时新增，案例来自既有真实记录，不能说成早期开发已使用它。

## 输入与版本归属

- 读取项目 `README.md`、`project-manifest.json`、`docs/代码日志对应表.md`，再找对应候选的 source-freeze、构建、RAM、功能、固化及冷启动收据。较新的状态覆盖旧快照，不抹掉旧失败。
- 用户指定的 PPT/视频保持原件；记录长度、大小、SHA256和适用版本。当前工作树、SDK副本、冻结源、实际加载镜像分别核对。不能用 source50 的未完成工作树冒充 R49/source49 重建源。
- 没有具体候选时，先列已有版本与缺失项；不要为补齐“通过”而重新跑硬件。移植与 RAM 操作属于项目现有 `k7-openvela-driver-port` 的职责，需有相应任务授权。

## 执行

1. 按“文件确实存在 → 哈希/长度 → 构建关系 → 实际加载 → 对应场景”核对。SHA一致证明文件身份，不证明场景通过；编译、GATT写成功、用户看到物理动作、冷启动与长期稳定性分别归档。
2. 对已知清单运行只读工具。脚本仅依赖 Python 3.10+ 标准库；先确认解释器版本，Windows 的旧 `python` 可能是3.6，应选用项目已有3.12解释器。下列`python`均指确认后的解释器，命令从项目根执行：

   ```text
   python -B skills/velavision-evidence-audit/scripts/verify_evidence_manifest.py --root . --manifest skills/velavision-evidence-audit/references/r49-evidence-manifest.json
   ```

   此内置清单只固定 2026-11-03 R49 的五个收据/测量文件，字段见 [清单与证据口径](references/evidence-contract.md)。新版本新建清单，不把失败的实际哈希改成期望值以获得通过。私有镜像或1081项源pin要另行核对，不假称该五文件检查覆盖了它们。
3. 性能先写计时起点/终点、时钟、样本量、缺失与失败样本，再给中位数/范围。板端播放状态不是外部声音起点；管线计时不包含用户说话和ASR收尾。发出检索选项不等于服务端真正调用检索，需 usage/调用回执支持。
4. 将主张分成“实测支持、用户现场反馈、推断、未验收”。没有原始支撑的强结论删去或降为待确认，具体 R49 案例见 [清单与证据口径](references/evidence-contract.md)。
5. 提交材料按实际表单字段核对：最终PPT、视频、实拍、更新说明、源码与AI日志目标仓/分支/许可。默认使用用户提供的已保存规则；若任务要求核对现行规则或实际提交，浏览赛事官方原页并记录日期与来源。不要把历史“四分钟”、至少一个Skill或评分比例当作永久规则。权限、大小和截止时间不能凭旧文案推断。

## 输出与停止边界

交付：材料清单与SHA、主张到收据的映射、缺失/限制、可公开摘要及内部备查清单。公开摘要使用相对文件名或角色名；不复制整个 `private/`、完整UART、服务凭据、原始人脸、业务任务ID和设备恢复镜像。实拍、设计图、屏幕截图分开标注；留有电脑线的照片不能独自证明完全脱离电脑运行。

发现哈希不符、来源歧义、快照正在变化或版本混用时，保留原数据并报告具体阻断项；不自动改收据、覆盖源码、启停服务或刷写。准备提交不等于已上传、已合入官方仓或已获外部发送授权；按当前用户指令决定最后一步，并报告实际完成状态。
